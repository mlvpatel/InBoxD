# Architecture
last_updated: 2026-04-21

This document describes the system architecture of the Email Classifier.

## Overview

The Email Classifier is an n8n workflow automation system that processes incoming emails through a two-stage LLM pipeline. Stage 1 extracts structured information and classifies the email intent. Stage 2 drafts a professional reply using only verified database values. The system enforces strict anti-hallucination controls by separating data retrieval from text generation.

## System Context

The system operates within the following boundary. External actors include email senders (vendors and customers), the Outlook email service, the LLM provider (OpenAI or Ollama), and the Excel database (OneDrive or local file).

See [C4 Context Diagram](diagrams/c4_context.mmd) for the visual representation.

## Container View

The system consists of the following containers.

1. **n8n Workflow Engine**: Orchestrates the entire email processing pipeline. Runs as a Docker container exposing port 5678. Manages workflow state, credential storage, and execution scheduling.

2. **LLM Service**: Provides natural language understanding and generation. In the cloud variant, this is the OpenAI API (gpt-4o-mini). In the local variant, this is an Ollama instance running qwen2.5:7b-instruct. The architecture supports swapping to any compatible LLM provider via the n8n LangChain node configuration.

3. **Excel Database**: The read-only data source containing inventory and delivery information. In the cloud variant, this is a Microsoft 365 Excel workbook on OneDrive accessed via the Microsoft Graph API. In the local variant, this relies on local Inventory and Deliveries .xlsx files read directly from the filesystem.

4. **Qdrant Vector Database** (local variant only): Provides embedding-based fuzzy product matching as a third matching tier. Stores product embeddings generated by bge-m3 via Ollama. Uses cosine distance with 1024-dimensional vectors.

5. **Outlook Email Service**: The email interface for receiving incoming messages and creating draft replies. Accessed via the Microsoft Graph API with OAuth2 credentials registered through Microsoft Entra ID.

## Component View

Within the n8n workflow engine, the following logical components exist.

1. **Email Ingestion** (Nodes 1 through 3): Handles trigger polling, triple-layer idempotency (Outlook isRead flag, in-memory rolling window, internet message ID), and thread stripping via regex-based marker detection.

2. **Classification** (Nodes 4 and 4b): Performs the Stage 1 LLM call and includes a Heuristic Language Override layer that applies regex-based language detection to safeguard against translation hallucinations (e.g., preventing Italian emails from being classified as English).

3. **Routing** (Node 5): A deterministic Switch node that directs the classified email to the appropriate data loading path based on intent. Supports three output branches: Unknown, Delivery, and Inventory. Fallback routes to the Unknown branch.

4. **Data Retrieval** (Nodes 6a, 6b, 7, 7u): Loads the relevant Excel sheet(s) and performs product matching using the tiered matching ladder (Exact, Substring, and optionally Embedding via Qdrant).

5. **Response Generation** (Nodes 8 through 11): Composes an intent-specific data packet (stripping internal fields like discount rates and categories), performs the Stage 2 LLM call, scrubs residual template placeholders and markdown formatting, and constructs the reply subject.

6. **Output** (Nodes 12, 13, and 14): Creates the Outlook draft (never auto-sends), records a structured log entry, and marks the original email as read to complete the idempotency loop.

See [C4 Component Diagram](diagrams/c4_component.mmd) for the visual representation.

## Data Flow

The email processing pipeline follows this sequence.

1. An email arrives in the monitored Outlook inbox.
2. The Outlook Trigger node detects the new message via polling and passes it to the pipeline.
3. The Dedup node asserts a Triple-Layer Idempotency check, querying the Outlook isRead flag, an in-memory rolling window (7-day TTL), and the internet message ID to block duplicate processing.
4. The Thread Stripper removes HTML tags and quoted reply history using six regex-based markers (English, Italian, and generic blockquote patterns), outputting clean text.
5. The Stage 1 LLM classifies the email and extracts structured fields (intent, product_name, customer_name, language, confidence), followed by a heuristic validation layer.
6. The Switch node routes the data based on the classified intent into three branches.
7. The relevant Excel sheet(s) are loaded and the Matcher performs tiered product lookup.
8. The Compose Data Packet node builds an intent-specific data object for the drafter, explicitly excluding internal fields.
9. The Stage 2 LLM drafts a reply using only the values in the data packet.
10. The Scrub Format node dynamically sweeps any residual template placeholders, markdown formatting, smart punctuation, and emoji.
11. The Compose Subject node prepends "Re:" to the original subject if needed.
12. The Create Outlook Draft node saves the reply as a draft in Outlook.
13. The Mark Processed node records the message flow in a structured log entry.
14. The Mark Email Read node updates Outlook status to isRead=true, completing the idempotency loop.

## Deployment

Both variants are deployed using Docker Compose. The cloud variant uses a single n8n container. The local variant uses three containers (n8n, Ollama, Qdrant) on a shared bridge network. Both variants use ngrok for OAuth callback tunneling during local development.

See [Deployment Diagram](diagrams/deployment.mmd) for the visual representation.

## Invariants

The following invariants are enforced across both variants.

1. The workflow makes exactly two LLM calls per email: one for extract and classify, one for draft.
2. The LLM never sees quoted email history.
3. The LLM never cites a value that is not in the data packet.
4. Drafts are never auto-sent.
5. Excel access is read-only.
6. Every run emits a structured log entry.
7. Internal pricing variables (discount rates, categories) are never exposed to the drafting LLM.
